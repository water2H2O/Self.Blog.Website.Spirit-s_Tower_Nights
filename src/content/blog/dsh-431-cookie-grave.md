某天早上点开 DSH 桌面版，窗口起来了，然后停在那一句：

```
desktop welcome: Web authentication failed
```

数据都在，聊天记录也在，就是进不去。重启、换网络、关杀软，全都没用。

这篇文章记一下最后查出来的东西，因为它不是偶发故障，而是**从装上的那天起就在倒计时**。

## 一、先怀疑的三件事，全错

第一反应是网络。本地起服务、打开回环地址，能连。

第二反应是端口占用。`--port 0` 本来就是让系统随机分配，理论上不会撞。

第三反应是杀软/防火墙。临时关掉，还是那句 `Web authentication failed`。

真正有用的线索是打开开发者工具之后那一行：**`431 Request Header Fields Too Large`**。

Node 的 HTTP 服务默认 `maxHeaderSize = 16384` 字节。超过这个体积的请求头，服务器在读的时候就直接拒了 —— 请求根本没走到应用逻辑，于是那句「认证失败」只是因为**服务端压根没看到认证头**。

## 二、这些字节是哪来的

看请求：

- 每次启动用 `--port 0`，端口随机
- 打开根路径时回 `303`，同时下发一个 cookie：`Set-Cookie: dsh-auth-<sha256("127.0.0.1:<端口>")>`
- cookie 是按 **host** 存的，而 host 里带端口 —— 端口一换，就是**另一个 host**

关键就在这：同一个 cookie 名，在不同端口下属于不同的 host，浏览器**不会覆盖**，只会新增。昨天 51201、今天 51202，那就是两条。

于是每启动一次，就多一块墓碑。

单条体积算一下：

| 片段 | 长度 |
|---|---|
| `dsh-auth-` | 9 |
| 名字部分（sha256 十六进制）| 43 |
| `=` | 1 |
| 值（base64 的 sha256）| 173 |
| `; ` | 2 |
| **合计** | **228 字节** |

`16384 ÷ 228 ≈ 71.86` —— 也就是说，**第 72 次启动**才开始报错。装了快两个月，这个数字一点也不夸张。

## 三、自查不用等它坏

既然规律是「每次启动 +228 字节」，那就可以提前量。

我写了个小工具（`cookie-guard`），常驻在屏幕右下角，读浏览器的 cookie 库，数一下这个 host 前缀下有多少条：

![Cookie 守护浮窗：环形仪表显示请求头占用 46%，下面三格是 33 条 cookie / 7.3K 请求头字节 / 还能启动 38 次](../../assets/oc/blog-cookie-guard.webp)

```json
{
  "dir": "C:\\Users\\…\\User Data\\Default\\Network",
  "matches": 33,
  "bytes": 7524,
  "usedPercent": 45.9,
  "remainingBoots": 38,
  "mode": "borrowed-handle"
}
```

33 条、7524 字节、用掉 45.9%，**还能启动约 38 次**。（浮窗上写 46% / 7.3K / 上限 71 条 —— 那是抹掉小数、按 KiB 显示的口径，同一份数据。）

这里「`mode: borrowed-handle`」是另一件事：Chromium 开着的时候 `Cookies` 这个 SQLite 库是**独占锁**的，直接复制会失败。所以要借句柄 —— 用 `NtQuerySystemInformation` 拿到全系统的句柄表，找到持有这个文件的进程，再 `DuplicateHandle` 复制一份出来读。听起来很重，其实就是「不关浏览器也能读」。

顺便说一句，第一次读到 33 条的时候我是有点发愣的：这个数字等于「我装好 DSH 之后开过 33 次以上」，而它一直在稳步往上走。

## 四、怎么修

1. **托盘图标右键退出**。不是点窗口的 ×（那只是关窗口，进程还在，cookie 库还锁着）
2. 备份 `Network\Cookies` 和 `Cookies-journal`（留着万一）
3. 删掉这两个文件
4. 重新打开，重新登录

清完就回到 0 字节，可以再安稳开机 71 次。

## 五、真正该记的教训

**持久化存储 + 随机端口 = 定时炸弹。**

写这种东西的时候，两条路选一条：

- **要么带清理**：启动时看看同名 cookie 有多少条，超了就清掉旧的（同一台机器上，旧端口的下一次也不会再用到）
- **要么别落地**：这种「一次会话内自证身份」的 token 放内存里就够了，本来就没有跨会话的价值

我的实现两条都没做，于是它成了一个每天缓慢逼近上限的计数器。而它触发的时候，表现成的是「应用坏了」，不是「你的 cookie 太多了」—— 这才是最难查的地方。

---

补一句：这个坑不需要等到第 72 次才发现。你只要知道「每启动一次 +228 字节」，剩下的就是算术。
