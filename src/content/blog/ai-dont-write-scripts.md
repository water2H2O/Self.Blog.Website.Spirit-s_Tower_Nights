起因很小：建文件夹的时候，名字里留了个空格。

等到要在里面开发东西、跑工具，我开始担心后面反复踩路径的坑，就想趁文件还不算多，把 `D:\vibe coding` 改成 `D:\vibe_coding`。

但这次并不是我打开资源管理器，直接改完名字，再发现 DSH 找不到目录。

**恰恰是为了避免这种事，我特意让 DSH 自己来做。**

我的想法很朴素：既然它一直在这个工作区里干活，让它处理改名和路径引用，应该比我直接改更稳妥吧。

后来才发现，能帮我操作文件，并不等于它知道自己所在的应用是怎样保存工作区和聊天记录的。

## 第一版：先退出 DSH，再运行它写的脚本

DSH 写了一份脚本，让我完全退出应用，再在外面的 PowerShell 窗口里运行。

这一步听上去很合理：应用还开着，目录和配置可能正在被使用；既然要动路径，先退出，至少能避免一边运行、一边修改。

于是我照做了。10 月 17 日，2:47，开始了这次本来以为很快就能结束的调整。

运行之后，出问题了。DSH 开始报错，目录无法正常读取，工作区也没法正常修改。原本是为了让改名之后还能顺利使用，结果先把自己卡在了门外。

出错以后跑诊断，结果里提到两个 bundle 没有安装，还有一个安装位置无法定位：

![当时 dsh-doctor 给出的诊断结果](../../assets/oc/blog-ai-dont-write-scripts-doctor.webp)

照着建议尝试补装，又遇到了 404：

![尝试补装缺失 bundle 时遇到的 npm 404](../../assets/oc/blog-ai-dont-write-scripts-npm404.webp)

一个说缺东西，一个说找不到。到了这里，我已经很难分清，究竟是最初的问题还没修好，还是修的过程中又碰上了别的问题。

当时的记录里，折腾到 3:40，我还是走到了删掉、重装这一步。应用重新能打开了，之前的聊天记录虽然留有备份，却没能恢复到原来的工作区状态。

## 回头看，它改的不只是文件夹名字

事后，我把第一版脚本交给在线 DSH 分析。它的复盘里有一句话，让我重新注意到了这份脚本的操作范围：

> “他做了 DryRun 预览、编码感知、排除了 SQLite 数据库、做了备份”，但“触碰了 DSH 的核心状态文件”。

这是一次事后分析，不是完整的故障鉴定。不过，对照留存的脚本，确实可以确认：它并不只是给文件夹改名、更新几处项目配置，而是把手伸进了 DSH 自己的数据目录。

第一版大致做了这些事：

| 位置 | 脚本里的处理方式 |
| --- | --- |
| 工作目录本身 | 改名，并递归扫描符合条件的文件，替换旧路径片段 |
| `.dsh/storages/workspace.json` | 直接在文件里按字符串替换路径，而非由应用执行迁移 |
| `.dsh/storages/session_projcache/sessions/` | 扫描部分会话缓存 JSON，替换其中匹配的内容 |
| `.dsh/sessions/` 下对应工作区的会话目录 | 把由旧路径生成的目录名，改成脚本预期的新名字 |

除此之外，它还处理了其他编辑器的状态目录和配置。这份工具的范围，已经远远超过“改一下这个文件夹名”。

不能说它完全没考虑安全。它有 `DryRun`、编码处理、部分数据库文件的排除规则，也会给一部分工作区外文件留备份。

但这些保护都有范围：工作目录树内的替换没有逐文件备份；外部文件的备份允许覆盖；所谓“排除数据库”依赖文件名规则，并没有把 DSH 的内部状态整体隔离开。`DryRun` 能列出准备修改的地方，也不能替应用验证改完之后是否仍然可用。

更重要的是，**文件能写进去，和应用能读懂写进去的状态，是两回事。**

目录名、工作区登记、会话缓存，需要彼此对得上。第一版却是分步改：某个文件处理失败后可以继续，目标会话目录已经存在时也可能直接跳过。最后检查的主要是新目录是否存在、旧路径字符串是否还残留，并没有实际验证 DSH 能否加载这些工作区和会话。

退出应用，避免的是运行期间的占用和并发写入；它并不会自动让一份外部脚本具备正确迁移内部状态的能力。

至于究竟是哪一次写入触发了哪条报错，单看脚本还不能完全定因。但有一点已经不含糊：我原本委托的是安全地调整工作目录，拿到的却是一份会直接修改应用内部状态的脚本。

## 第二版：想把聊天记录接回来，结果又回到了报错

第一次没能恢复好，我还是让 DSH 继续想办法。

它又写了第二版脚本。这次的目标不是重新改名，而是把恢复出来的旧会话，与当前环境合并起来，把之前的沟通和工作区重新接上。

脚本要求先完全退出 DSH，备份当前的一部分数据，再做合并：

- 将暂存目录里的旧会话复制进当前的 `sessions`；
- 合并会话缓存和附件，遇到同名目标则跳过；
- 读取新旧两份工作区清单，按路径合并会话 ID，重新写入 `workspace.json`；
- 同时处理工作区列表，以及归档、置顶等会话登记。

这里需要说准确一点：它**没有直接解压、改写聊天正文**。它动的是旧会话文件的归入位置，以及这些会话如何登记在工作区里。对使用者而言，这些同样决定了“我的聊天记录还能不能在原来的地方打开”。

而第二次运行之后，还是类似的问题：报错，工作区状态没有恢复。试了多次，也没能把那些记录顺利接回来。

回头看第二版，最值得警惕的，是它把“文件复制过来了”和“状态恢复好了”靠得太近了。

比如，同名会话目录会整块跳过，不能保证里面原本就完整；工作区清单则按照脚本列出的字段重新组装，再把旧会话 ID 并进去。新生成的 JSON 会做一次解析检查，但那只能说明它在语法上是 JSON，不能证明它符合当前 DSH 的要求，也不能证明清单、缓存、会话和附件之间的引用都成立。

备份也不是整个 `.dsh` 的完整快照。即使把备份文件复制回去，也不等于自动撤销合并时新增的一切。

这不是说其中每一项风险都在我机器上发生过，而是它们说明了一个问题：**“修复完成”的输出，缺少一次真正由应用验证的恢复结果。** 对我来说，能重新打开原来的工作区和对话，才叫恢复。

## 最后，我把那个目录改了个名字，停下了

到这一步，应用怎么重新起起来，我已经有点经验了。

找到 `.dsh` 文件夹，右键重命名，把它隔离成：

```text
.dsh_broken_20261017
```

这一次不再继续往旧状态里合并、替换，而是把它留在一边，让应用在新环境里重新开始。

注意，这里只是我最后的止损动作，不是一条可以照抄的通用恢复命令。隔离旧目录，也不等于聊天记录已经恢复。

那个文件夹现在还安静地躺在资源管理器里。我没有把它删掉，但也已经不想再尝试恢复数据了。

不是证明了它绝对救不回来，而是我不想再拿当前能用的环境，去赌下一份“这次应该可以”的脚本。

## 有备份，不等于能接着用

此前的复盘里，我还提到过工作区的权限继承异常。它是排查中需要单独处理的问题，但不能拿来概括这整次事故，更不能因此把两版脚本对内部状态的修改略过去。

现在更清楚的经过是：为了避免改名后失联，我让 DSH 自己生成迁移脚本；运行后报错，再让它生成恢复脚本；合并旧会话之后，还是没能恢复工作区状态。最后能做的，是把旧数据隔离下来，重新搭环境。

这件事也改变了我对“备份”的理解。文件还在，和它们能被应用正确加载，并不是同一个承诺。尤其是聊天记录，光保住正文，还不一定能保住原来的工作区、附件和会话关系。

还有一个很实际的教训：**都用 DSH 了，就先把自己的 DeepSeek 账号登录上去，不要图省事。**

不过这也只是我以后会做的事，不是“登录账号就一定不会丢数据”的保证。云端到底保存哪些历史，附件和工作区状态能同步多少，真遇到类似事故又能恢复多少，我现在并不清楚。账号、同步和本地备份，不能不加区分地当成同一件事。

## AI 可以帮忙，但操作边界得先划好

这篇最初的标题是“AI 还是别写脚本了吧……”。现在我仍然能理解当时为什么会这么说。

那次不是我无视提醒、在应用还开着的时候乱跑脚本。我为了稳妥，特意让 DSH 自己处理，也照着它的要求完全退出了。流程看起来挺周到，结果还是出了问题。

用来运行模型的工具，并不会因此让模型天然懂得这套工具的底层存储机制。脚本写得像模像样，有注释、有备份、有预览，也不代表它对这些内部状态的理解已经经过验证。

所以以后我会把边界说得更明确：

- 项目代码和普通文本，可以在版本控制、差异检查的范围内改；
- 应用自己的工作区清单、聊天记录和内部状态，不因为“里面也是 JSON”就允许直接批量替换；
- 真要做迁移或恢复，先查官方支持的办法；需要试验，也应该在独立副本里验证，而不是直接写回正在使用的数据目录；
- 第一轮已经失败，就先停下来保全现场，不把下一份“修复脚本”当成天然更安全的选择。

我找 AI 是为了省事，不是为了在出事之后，接手一整套自己本来不需要懂的恢复工作。

说到底，真要弄坏了，承担后果的还是我。聊天记录回不来，要继续使用的环境得重搭，已经花掉的时间也不会有人替我补回来。这条操作红线，得在按下运行之前划好。

它还在那里。至于里面那些对话，这次我选择先不救了。
