这篇讲两个坑，都是生图接进 agent 时踩的。第一个会让你以为方案成了，然后账单到了。

## 一、一开始的接法：把它当聊天模型

`gpt-image-2` 是 OpenAI 兼容接口，那最省事的接法就是：**当成一个普通 LLM provider 配进去**。

```
provider: gpt-image-2
baseURL:  .../v1
model:    gpt-image-2
```

然后它真的能用。你问它「画一只坐在水塔上喝茶的狐狸」，它返回：

```
![generated image](data:image/png;base64,iVBORw0KGgoAAAANSUhEUg…)
```

图片就在对话里，agent 还能接着聊、接着改。当时觉得这事成了。

## 二、问题在体积

那个 base64 有多大？实测：

| 路径 | 耗时 | 响应体 |
|---|---|---|
| `/v1/images/generations` | 47 s | 1.9 MB |
| chat 接口（当聊天模型用）| 26–37 s | **3.9–5.9 MB** |

按 4 个字符 / token 粗算，5 MB ≈ **125 万 token**。

单张图一百多万 token —— 这个数字本身只是「贵」，还不是最要命的。

## 三、真正的问题：它每次重读都重新计费

关键在于 **base64 塞在对话历史里，而且不可缓存。**

上下文每轮都要重发一遍。假设一个 20 轮的会话，第一轮那张图会在后面 19 轮里被反复读：

```
一轮 100–150 万 token × 20 轮 ≈ 2000 万 token
```

账单不会写「你花在 20 张图上」，它会写「你花了 2000 万 token」，全都记在那**一张图**头上。

### 两种算法，只有一种说得清

| 口径 | 算法 | 结果 |
|---|---|---|
| A. 把 base64 当上下文 | 3.9 MB ÷ 4 ≈ 97.5 万 token，按重读 12 轮 ≈ 1170 万 token × ¥0.9/M | ≈ ¥10 / 张 |
| B. 折算「有效信息」| 单张成本 ≈ ¥0.1，真正有用的信息 ≈ 1000 token | ≈ **¥104 / 百万 token** |

我更愿意用 B 来讲这件事，因为它说明的**不是涨价，是稀释**：

> 你付的钱没变，但买到的东西被稀释了 1000 倍。

一张图的价值是「这张图」，不是「五兆的 base64」；把它当上下文，等于为同一张图反复付 20 次钱。

## 四、正确做法：当工具，不当对话

把生图做成 **tool**，而不是塞进上下文：

1. 调 `/v1/images/generations`
2. 从 `data[0].b64_json` 取图
3. **存盘**
4. 只把**文件路径**返回给对话

于是不管会话聊多少轮，上下文里始终只有一行字符串：

```
/Users/…/20261028-021722-一只橘色狐狸坐在水塔顶上喝茶.png
```

单张图进上下文的 token ≈ **0**。实测最终方案：36.7 s / 1.72 MB 落盘。

同一个需求，成本差两个数量级，区别只是**图片经过对话，还是绕过对话**。

## 五、第二个坑：旧式 thinking 参数直接 400

换到 `claude-opus-5-5` 的时候撞上这个：

```
400 … requires adaptive thinking
```

原因是它**只接受** `thinking.type = "adaptive"`，老写法 `enabled + budget_tokens` 一律拒。这种「接口长得一样、参数语义变了」的地方最容易踩，因为客户端代码通常按旧规范写的。

## 六、兜底：可以回退，但别把 base64 放进对话

images 接口偶尔会 502 / 503。合理的兜底是**回退到 chat 接口**，但有个前提：

> 解析必须在脚本内部完成。

也就是：chat 返回的 base64 在脚本里被解出来、存盘、只把路径吐出去。**任何时候都不要让那个 base64 流进对话历史**，否则兜底逻辑会把前面省下的钱一次还回去。

## 七、小结

| 做法 | 图片进上下文的量 |
|---|---|
| 当聊天模型 | 100 万+ token / 张，且每轮重读 |
| 当工具（推荐）| ≈ 0，只传路径 |

三条可以直接抄走的结论：

1. **生图不进上下文**，落盘传路径
2. **推理模型注意 `max_tokens`**，思考也吃额度
3. **按「有效信息单价」算账**，别只看单次请求多贵
